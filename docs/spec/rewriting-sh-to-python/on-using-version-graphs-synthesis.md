The diagram illustrates the skos-history approach for representing versions and deltas of a SKOS vocabulary as named graphs in a SPARQL 1.1 dataset. It shows how two complete versions of a vocabulary, here “STW 8.14” and “STW 9.0”, are connected through an explicitly modelled delta. The delta is decomposed into two named graph components: an insertions graph and a deletions graph.

The model should be understood as a version store for a SKOS concept scheme. A version store is an RDF dataset in which each complete version of the vocabulary is loaded as a separate named graph. In this example, one named graph contains the old version “STW 8.14”, and another named graph contains the new version “STW 9.0”. The version data themselves remain in these named graphs. The surrounding metadata describes which graph corresponds to which version, how the versions are ordered, which version is current, and which graphs contain the computed differences between versions.

The blue resources on the right represent version-history metadata. The two `dsv:VersionHistoryRecord` resources represent individual version records. One record describes version “8.14”, and the other describes version “9.0”. These records are not the version graphs themselves. They are metadata resources about the corresponding versions. Each version history record is linked to a named graph description using `sh:usingNamedGraph`.

In the skos-history pattern, the object of `sh:usingNamedGraph` should be understood as an `sd:NamedGraph` resource, not merely as a raw graph IRI. The `sd:NamedGraph` resource then identifies the actual named graph through `sd:name`. This distinction matters because the model separates graph metadata from the graph IRI itself. A query should therefore retrieve the graph IRI through a path such as `sh:usingNamedGraph / sd:name`.

The pale blue `dsv:VersionHistorySet` represents the version history as a whole. It groups the version history records that belong to the same evolving vocabulary. In the example, both the “8.14” and “9.0” records belong to the same version history set. The version history set also identifies the current version record using `dsv:currentVersionRecord`. In the diagram, the current version record is “9.0”.

The version history set is also associated with a SPARQL endpoint using `void:sparqlEndpoint`. This indicates where the version store can be queried. The endpoint provides access to the named graphs containing the full versions, the insertions, the deletions, and the version history metadata. In a complete SPARQL service description, the individual named graphs may also be declared as `sd:NamedGraph` resources.

The chronological relationship between the two version records is represented using `xhv:prev`. The “9.0” version history record points to the “8.14” version history record with `xhv:prev`. This states that version 8.14 is the previous version of version 9.0. The relation gives the version chain independently of the delta object.

The central orange resource, `sh:SchemeDelta`, represents the delta between the two versions of the SKOS concept scheme. It is the explicit change object for the transition from the old version to the new version. It has a source version and a target version. The property `sh:deltaFrom` links the delta to the source version record, here “8.14”. The property `sh:deltaTo` links the delta to the target version record, here “9.0”.

The `sh:SchemeDelta` is decomposed into two parts. The first part is a `sh:SchemeDeltaInsertions` resource. This represents the graph of triples that are present in the new version but not in the old version. The second part is a `sh:SchemeDeltaDeletions` resource. This represents the graph of triples that are present in the old version but not in the new version.

The part-whole structure is expressed using Dublin Core Terms. The overall `sh:SchemeDelta` has parts via `dcterms:hasPart`. The insertion and deletion components point back to the overall delta using `dcterms:isPartOf`. This makes the delta navigable in both directions: from the whole delta to its insertion and deletion components, and from each component back to the delta to which it belongs.

The insertions and deletions are materialised as separate named graphs. The insertion component uses a named graph containing all inserted triples. The deletion component uses a named graph containing all deleted triples. This means that clients do not need to recompute the difference between the old and new versions every time they want to inspect changes. The graph differences are precomputed and can be queried directly.

Formally, if the old version graph is O and the new version graph is N, the insertions graph contains the triples in N that are not in O. The deletions graph contains the triples in O that are not in N. The skos-history loading approach computes these differences using SPARQL `MINUS`. For deletions, the old graph is the minuend and the new graph is the subtrahend. For insertions, the new graph is the minuend and the old graph is the subtrahend.

The model deliberately treats insertions and deletions as graph-level deltas. This is a lower-level, triple-oriented representation. Higher-level change categories can then be derived by querying patterns over these insertion and deletion graphs. For example, if a concept appears in the new version and not in the reference version, it can be interpreted as a new concept. If a concept existed in the reference version but is no longer present in the new version, it may be interpreted as a removed concept. If an active concept becomes deprecated, it can be classified as a deprecated concept.

Other higher-level change categories include new and removed collections, new and removed semantic relations, changes to broader, narrower, related, or matching relationships, changes in collection membership, concept merges, concept splits, new labels, removed labels, changed preferred labels, changed notations, moved alternative labels, and note changes. These categories are not necessarily directly asserted in the basic graph model. Rather, they can be computed or reported from the raw insertion and deletion graphs.

This distinction is important. The diagram shows the infrastructure for representing version-level and triple-level change. It does not itself show all possible semantic interpretations of change. The higher-level changes are analytical views over the delta graphs. They are useful for human indexers, vocabulary maintainers, mapping maintainers, derived vocabulary maintainers, automatic indexing systems, and search applications.

The model is particularly suitable for SKOS thesauri and controlled vocabularies because such resources evolve over time and often have downstream users who need to understand what changed. A human indexer may need to adapt to a new vocabulary version. A collection manager may need to re-index resources affected by changed concepts or labels. A mapping maintainer may need to inspect whether changes in one vocabulary affect mappings to another vocabulary. An automatic indexing or search system may need a machine-readable change structure to update its behaviour.

From an OWL/RDFS modelling perspective, `sh:SchemeDelta`, `sh:SchemeDeltaInsertions`, and `sh:SchemeDeltaDeletions` are classes in the skos-history vocabulary. `sh:SchemeDelta` denotes the delta of two versions of a SKOS concept scheme. `sh:SchemeDeltaInsertions` and `sh:SchemeDeltaDeletions` denote the two delta components. The skos-history ontology models these delta resources as subclasses of `skos:ConceptScheme`, which reflects the fact that the delta graphs may themselves contain SKOS-relevant structures and can be queried as concept-scheme-like resources.

The property `sh:usingNamedGraph` connects a version record or delta component to an `sd:NamedGraph` description. Its range is `sd:NamedGraph`. The `sd:NamedGraph` resource identifies the actual graph through `sd:name`. The graph description may also be included in a SPARQL service description, making the available version and delta graphs discoverable.

The property `sh:deltaFrom` has `sh:SchemeDelta` as its domain and points to the version from which the delta is taken. In practice, its object may be a `dsv:VersionHistoryRecord`. The property `sh:deltaTo` also has `sh:SchemeDelta` as its domain and points to the version to which the delta is taken. Together these properties define the direction of the delta.

The property `sh:hasDelta` links a version history record to a delta associated with that version. In the most useful interpretation, the target version record has a delta explaining how it was obtained from the previous version. In the diagram, the delta from “8.14” to “9.0” is discoverable from the version records and is explicitly anchored by `sh:deltaFrom` and `sh:deltaTo`.

The property `dsv:hasVersionHistorySet` connects a version history record to the version history set it belongs to. The property `dsv:currentVersionRecord` connects the version history set to its current version record. The property `xhv:prev` links a version record to its previous version record. These properties together support navigation from the version history set to the current version, from the current version to its predecessor, and from the version pair to the corresponding delta.

From a SHACL perspective, the diagram suggests several useful validation shapes, even if the skos-history ontology itself is not a SHACL shapes graph. A shape for `dsv:VersionHistorySet` should require exactly one `dsv:currentVersionRecord`, and the value should be a `dsv:VersionHistoryRecord`. It may also require a `void:sparqlEndpoint`, because the version store is intended to be queryable through a SPARQL endpoint.

A shape for `dsv:VersionHistoryRecord` should require membership in a version history set through `dsv:hasVersionHistorySet`. It should normally require a graph description through `sh:usingNamedGraph`, whose value should be an `sd:NamedGraph` with an `sd:name`. For non-initial versions, it may require an `xhv:prev` link to the previous version history record.

A shape for `sh:SchemeDelta` should require exactly one `sh:deltaFrom` and exactly one `sh:deltaTo`. Both values should be version history records. The source and target version records should not be the same resource. The shape should also require one insertion part and one deletion part, expressed through `dcterms:hasPart` and qualified by the classes `sh:SchemeDeltaInsertions` and `sh:SchemeDeltaDeletions`.

A shape for `sh:SchemeDeltaInsertions` should require that the resource is part of exactly one `sh:SchemeDelta` through `dcterms:isPartOf`. It should also require exactly one `sh:usingNamedGraph` value. The named graph description should have an `sd:name` pointing to the graph that contains the inserted triples.

A shape for `sh:SchemeDeltaDeletions` should mirror this pattern. It should require membership in exactly one delta and exactly one named graph description. The named graph should contain the deleted triples.

Additional SHACL-SPARQL constraints could validate the consistency of the delta. For example, every triple in the insertion graph should exist in the target version graph and not in the source version graph. Every triple in the deletion graph should exist in the source version graph and not in the target version graph. Such constraints would move beyond structural validation and into semantic consistency checking of the version store.

Another useful validation rule is alignment between `xhv:prev` and the delta direction. If a current version record has previous version record P, and a delta D points to the current version through `sh:deltaTo`, then D should point from P through `sh:deltaFrom`. This ensures that the version sequence and the delta relation tell the same story.

The model can also be related to VANN. `vann:changes` may be used as a lightweight annotation from a vocabulary description to a resource describing the changes between that vocabulary version and the previous version. In this model, such a target resource could be the `sh:SchemeDelta` or a human-readable change report derived from it. However, `vann:changes` does not replace the skos-history version-store pattern. It is an annotation property, not a full versioning model.

The model can also be compared with RDF Patch. RDF Patch records changes made to an RDF dataset and is useful for operations such as replication and incremental backup. The skos-history model is different in emphasis. It is not primarily a transaction log. It is a queryable publication structure: full vocabulary versions and their computed deltas are exposed as named graphs, with metadata that allows clients to discover the current version, previous versions, insertion graphs, deletion graphs, and related change information.

In practical use, the publication workflow is as follows. A publisher loads each complete vocabulary version as a named graph. For every pair of successive versions, the publisher computes the deletion graph as the triples in the old version but not in the new version, and the insertion graph as the triples in the new version but not in the old version. The publisher creates a `sh:SchemeDelta` resource, links it to the source and target version records, creates insertion and deletion component resources, links those components to their named graph descriptions, and updates the version history graph so that the version history set points to the current version record.

The resulting version store supports both simple and advanced queries. A client can ask which version is current, which graph contains the current version, what the previous version was, which delta connects the two versions, where the insertion and deletion graphs are, which concepts were newly introduced, which labels changed, which relations were added or removed, and which changes are relevant to a particular branch of the vocabulary or mapping context.

The diagram therefore represents a layered architecture for vocabulary versioning. At the graph layer, complete versions and deltas are stored as named graphs. At the metadata layer, version records, named graph descriptions, delta resources, and version history sets describe those graphs. At the query layer, SPARQL can retrieve both raw triple-level differences and higher-level change categories. At the validation layer, SHACL can be used to check structural completeness and consistency. At the application layer, the same data can support human indexers, vocabulary maintainers, mapping maintainers, derived vocabulary maintainers, automatic indexing systems, and search systems.

Overall, the image should be read as a precise RDF publication pattern for versioned SKOS vocabularies. It combines the Dataset Versioning vocabulary, the skos-history vocabulary, VoID, SPARQL service description vocabulary, Dublin Core Terms, and XHTML vocabulary terms. Its central contribution is to make vocabulary evolution explicit, queryable, and reusable by representing full versions and their insertions/deletions as named graphs connected by a version-history graph.
